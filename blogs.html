How I built “Ask Roshna AI”, a portfolio chatbot with no API key

Recruiters and hiring managers skim portfolios. I wanted a way for them to ask a question like “Has she used FastAPI?” and get a straight answer in a second, instead of hunting through sections. So I built a small assistant into my site. This is how it went, including the parts that broke.

The constraint: a static site

My portfolio is a static page on Vercel. Calling an LLM API directly from the browser means shipping an API key to every visitor, which is a bad idea. A backend would fix that, but I wanted something that works on day one. So I started with client-side retrieval: no server, no key, and answers that only come from facts I wrote myself.

Honest label: this is keyword retrieval over a hand-written knowledge base. It is closer to a smart FAQ than a full vector-search RAG system, but it follows the same retrieve-then-answer shape, and that made it easy to upgrade later.

The design in three steps

  1. Knowledge base. An array of entries, each with an id, a list of keywords and an answer() function that returns a short HTML snippet (projects, skills, experience, education, contact and so on).
  2. Retrieval. Tokenize the question, drop stop words, then score every entry by keyword overlap and take the best one.
  3. Response. Return that entry’s answer, or a friendly fallback listing what the bot can talk about. 
function retrieve(question) {
  var tokens = tokenize(question);          // lowercase, strip stop words
  var scored = KB.map(function (entry) {
    var score = 0;
    tokens.forEach(function (t) {
      entry.keywords.forEach(function (kw) {
        if (kw === t) score += 3;           // exact match
        else if (kw.length > 3 && t.length > 3 &&
          (kw.indexOf(t) > -1 || t.indexOf(kw) > -1)) score += 1; // fuzzy
      });
    });
    return { entry: entry, score: score };
  });
  scored.sort(function (a, b) { return b.score - a.score; });
  return scored[0].score > 0 ? scored[0].entry : null;
}

Exact keyword hits are worth three points and partial matches one. It is simple, fast, and easy to debug when an answer looks wrong.

The interface

The chat is a floating button that opens a panel with a welcome card, clickable suggested questions, a typing indicator and a send box. One detail I care about: user text goes through an escapeHtml() step before it is rendered, since answers are inserted as HTML and I don’t want visitors injecting markup into my own page.

Three bugs that bit me

1. The chat looked completely unstyled

My HTML and JavaScript used ai-* class names while the CSS defined rn-* ones. Nothing matched, so the widget rendered as plain text at the bottom of the page. Lesson: pick one naming prefix and search the whole file before shipping.

2. A missing })();

The last script block never closed its wrapper function. That is a syntax error, so none of the chat code ran, and the button did nothing. Lesson: check the browser console first; it told me immediately.

3. Tiny keywords matched everywhere

Keywords like hi, ui and ai matched inside unrelated words, so the wrong answers came back. The fix was to allow partial matching only for words longer than three characters, as in the code above.

Upgrading to a real LLM

I left a hook in the send function: if window.ASK_ROSHNA_API is set, the question is posted to that URL and the reply is shown; if the request fails, it falls back to the local knowledge base. The plan is a small FastAPI endpoint that does real retrieval over my content and calls an LLM, with the key kept safely on the server.

What I learned

  • Start with the simplest thing that works, but design it so the real version can slot in.
  • Answers are only as good as the knowledge base, so keeping it accurate matters more than clever scoring.
  • Most “AI feature” bugs are ordinary front-end bugs: naming, syntax, and edge cases in string matching.

Next on my list: embeddings and a vector store for proper semantic search, and streaming responses.

From client-side RAG to a real FastAPI backend — how I upgraded Ask Roshna AI

The first version of my portfolio chatbot worked entirely in the browser: a hand-written knowledge base, a keyword scorer, and a template response — no server, no API key. It was the right starting point, but I always planned to give it a real brain. This post is about how I built that upgrade using FastAPI, OpenAI, and a proper RAG pipeline.

Why move to a backend at all?

Three reasons. First, the client-side version could only do keyword matching — it couldn't handle paraphrased questions or give nuanced answers. Second, calling OpenAI directly from the browser would mean shipping an API key to every visitor, which is a non-starter. Third, I wanted a clean hook I could later swap for any LLM without touching the frontend at all.

The design goal: the frontend should not know or care whether the answer came from OpenAI, a local model, or a knowledge base. It just posts a question and renders the reply.

The API — one endpoint, two steps

The backend is a small FastAPI app with a single POST route at /ask. It accepts a question and an optional history array (for multi-turn context), and returns an answer and a source field so the client knows which path fired. 

class AskRequest(BaseModel):
    question: str
    history: Optional[list] = None   # last N turns

class AskResponse(BaseModel):
    answer: str
    source: str  # "openai" or "local-rag"

Inside /ask, two things happen in order.

Step 1 — Retrieval

I reused the same knowledge base from the client-side version, but moved it to Python. retrieve_context() tokenizes the question, strips stop words, scores every entry by keyword overlap, and returns the top three content blocks. Exact keyword hits score three points; partial overlaps score one. 

def retrieve_context(query: str, top_k: int = 3) -> list[str]:
    tokens = tokenize(query)
    scored = []
    for entry in KNOWLEDGE_BASE:
        score = 0
        for token in tokens:
            for keyword in entry["keywords"]:
                if keyword == token:
                    score += 3
                elif keyword in token or token in keyword:
                    score += 1
        if score > 0:
            scored.append((score, entry["content"]))
    scored.sort(key=lambda x: x[0], reverse=True)
    return [content for _, content in scored[:top_k]]

It is still keyword-based, not vector-based, but the retrieval quality is good enough for a focused knowledge base like this. The upgrade path to ChromaDB or pgvector is a one-function swap.

Step 2 — Generation

If OPENAI_API_KEY is set, the retrieved context is injected into a system prompt and sent to gpt-4o-mini along with the last four messages of chat history. If the key is missing or the OpenAI call fails, the endpoint returns the raw retrieved context chunks instead — no crash, no empty response. 

SYSTEM_PROMPT = """You are Ask Roshna AI…
Answer questions about Roshna using ONLY the context provided below.

Context from Roshna's knowledge base:
{context}
"""

messages = [{"role": "system", "content": SYSTEM_PROMPT.format(context=context_text)}]
if req.history:
    messages.extend(req.history[-4:])   # last 2 turns
messages.append({"role": "user", "content": req.question})

The fallback chain

I care about this more than the happy path. The backend has three tiers:

  1. OpenAI is available → LLM-generated answer grounded in the retrieved context.
  2. OpenAI fails or is not configured → raw retrieved content blocks joined as plain text.
  3. Nothing matches in the knowledge base → a friendly "I don't know, but I can help with…" message.

The frontend never sees an error. It always gets an answer of some kind.

Connecting the frontend

I left a one-line hook in the client-side chatbot: if window.ASK_ROSHNA_API is set before the script runs, the question is POSTed there and the reply is rendered; if not, it falls back to local matching. So pointing the portfolio at the FastAPI backend is a single assignment: 

window.ASK_ROSHNA_API = "https://your-api-host/ask";

No other frontend changes needed. This is the part I'm most pleased with — the two modes are genuinely independent and the seam between them is invisible to the user.

CORS and deployment

The backend reads ALLOWED_ORIGINS from the environment, defaulting to * for local development. In production I'll pin it to the Vercel domain. The app itself can be deployed on any host that runs Python — Railway, Fly.io, or an AWS Lambda behind API Gateway using Mangum.

What's next

  • Replace keyword scoring with real vector embeddings via the OpenAI embeddings API and store them in pgvector or ChromaDB.
  • Add streaming responses so the answer types out word by word instead of appearing all at once.
  • Cache frequent questions so repeated "Has she used FastAPI?" hits don't cost a token.

How I built this portfolio — every design decision, animation, and mistake

Most developer portfolios are either over-engineered React apps or bare-bones single pages. I wanted something in between: fast, static, visually interesting, and something I could actually maintain. Here is every decision I made building it, including the ones I had to undo.

One HTML file, no build step

The whole thing — hero, about, skills, experience, projects, education, contact form, AI chatbot — lives in a single index.html. No Webpack, no npm, no bundler. It deploys to Vercel in seconds and loads in under a second on a cold visit. The trade-off is that the CSS and JavaScript are inline, which makes the file long. For a portfolio that one person maintains, that is a fine trade.

Rule I followed: every feature has to earn its place. If removing it makes the page simpler without losing information, it goes.

Dark mode — system preference first, manual override second

I wanted dark mode to work without a flash of unstyled content. The approach: CSS custom properties for every colour, a prefers-color-scheme media query that swaps them automatically, and a data-theme attribute on <html> for the manual toggle. The toggle reads localStorage and applies the saved preference before the first paint. No JavaScript flash, no white-then-black flicker. 

try { s = localStorage.getItem("theme") } catch(e) {}
if (s) root.setAttribute("data-theme", s);

The try/catch around localStorage is not paranoia — in some privacy modes it throws. One line saves a confusing bug report.

The animated preloader

The loading screen shows $ npm run dev with a blinking cursor and a progress bar. It runs for 1.1 seconds then fades out. The whole effect is CSS — a @keyframes preLoad animation on a bar element and a steps(1) cursor blink. No JavaScript timer needed. I added it because the font loading occasionally caused a layout shift, and the preloader gives the fonts time to arrive without the user seeing the fallback stack.

The SVG doodle and 3D scene

The hero right column started as an SVG: a hand-drawn-style illustration of someone coding, with CSS animations for floating, blinking, steam rising from a coffee mug, and a twinkling star. It works everywhere including reduced-motion mode (all animations are gated on prefers-reduced-motion).

Later I added a Three.js alternative: six rotating cubes labelled with tech logos (Python, React, Node.js, FastAPI, AWS, MongoDB) orbiting a centre point in 3D space. The page detects WebGL support at runtime — if it works, the 3D scene replaces the SVG; if not, the SVG stays. The progressive enhancement means the page never looks broken on a device that can't do WebGL.

Scroll-driven reveals

Sections start with opacity: 0; transform: rotateX(10deg) translateY(40px). An IntersectionObserver adds an .in class when a section enters the viewport, triggering a CSS transition. I used a 3D rotate-in rather than a simple fade because it looks like the content is "landing" on the page. The whole thing is twelve lines of JavaScript and two CSS rules.

The projects section

Projects are filterable by tag. Each card has a data-tags attribute and filter buttons toggle an aria-selected state that drives visibility. The filter logic is a forEach loop — no library needed. Cards animate in with a staggered pop keyframe using a --i CSS custom property as the delay index.

One thing I made sure to include: a note that most of my professional work is for industry clients and can't be shown publicly. I'd rather be honest about that than have a recruiter wonder why there are only two GitHub links. The projects I can talk about — the AI Risk Intelligence Platform at SwarmLens and the Sharon Pipes Reward Program at Faircode — are described in detail, with the full tech stack and my specific role.

The contact form

Powered by Formspree. It validates client-side (empty name/email/message), shows inline errors in a monospace font to match the developer aesthetic, and replaces the form with a success message on submit. No server needed, no SMTP credentials to manage.

Three things I would do differently

1. Start with a naming convention

I ended up with a mix of class names from different drafts — some prefixed ai-, some unprefixed. It made the CSS hard to scan. I should have picked a prefix (rn- for Roshna N) and stuck with it from day one.

2. Separate the chatbot into its own file

The Ask Roshna AI widget is about 300 lines of JavaScript inside a <script> tag. It works fine, but it would be easier to test and iterate on as a separate module loaded with a <script src>.

3. Write the blog earlier

I added the blog section after the portfolio was already live. If I had planned for it from the start, the navigation and URL structure would have been cleaner from day one instead of being retrofitted.

The result

A fully static site deployed on Vercel with no build step, a perfect Lighthouse score, dark mode, a 3D hero scene with graceful fallback, a working AI chatbot with a FastAPI upgrade path, and a blog. It represents how I actually think about building things: start simple, make it work, then layer in the interesting parts.
